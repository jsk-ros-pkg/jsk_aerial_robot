# アーム先端のワールド定位：設計とGazebo評価

## 今回の目標と成立範囲

機体が位置・姿勢ともに揺れるときに、アームだけでTCP（作業点）をワールドに固定する。
機体の飛行制御は既存のものを利用し、先端補償のために機体の目標を変える制御は行わない。
評価時だけ、別の試験入力として飛行目標を揺らす。

現モデルのTCPまでの可動関節は `arm_joint1_joint1` 〜 `arm_joint4_joint1` の4軸。
`arm_joint5_joint1` はグリッパ駆動用で、URDF上もTCPの直列チェーンには含まれない。
従って一般のベース6自由度変動に対して、先端6自由度の完全固定はできない。
初版は **位置3軸を優先し、位置を局所的に変えない関節運動の範囲で姿勢誤差を最小化** する。
姿勢3軸の残差は隠さず、位置と別に評価する。

TCPの仮定は `arm_gripper_base_link` の `[0, 0, 0.047] m`。
指の中間の作業点を想定した仮のオフセットであり、実物の接触点を校正したものではない。
`--tcp` で置き換える。開閉する指自身や把持物の姿勢まで検証したことにはならない。
特にGazeboのmimic関節と実機のグリッパ機構は別途検証が必要。

## 制御

`arm_world_core.py` はROSに依存せず、展開済みURDFから固定関節を含むチェーンを読み取る。
`fc` はアームの祖先ではないため、共通のルートからの変換を介して正しく基準を変換する。

```
T_world_tcp = T_world_fc × FK_fc_tcp(q)
T_fc_tcp_desired = inverse(T_world_fc) × T_world_tcp_target
```

離陸・整定後のTCPを目標として一度固定する。比較する2試行は同じワールド目標を使う。
数値ヤコビアンの位置成分を主タスクにし、切り捨てSVDの擬似逆で位置誤差を補償する。
姿勢誤差はSO(3)の回転ベクトルで求め、位置ヤコビアンの零空間に投影して減衰付きで解く。
位置優先は局所的なものなので、離散時間・特異点・制限付近では位置残差も発生する。

30 Hzで位置サーボ目標を更新し、指令積分は直前の指令角を基準にする。
URDF関節範囲から0.05 radの余白を取り、速度にはURDFの各関節上限をそのまま使う。
関節角の実測は現在TCPの計算、初期化、入力の有効性判定と記録に使う。
XL430-W250・12 V電源を前提に、アーム5軸のURDFを61 rpm = 6.387905 rad/s、effort 1.5 N·mにそろえた。
根拠は[ROBOTIS公式仕様](https://emanual.robotis.com/docs/en/dxl/x/xl430-w250/)。
速度は無負荷値、トルクはストール値であり、同時に出せる連続性能ではない。
URDFの独立した上限のみで、電圧降下・温度・電流制限・トルク速度曲線はモデル化していない。
既存の質量・慣性・減速比・機械的な角度範囲は今回変更していない。
初期動画・試験で使った0.6 rad/sはプログラム独自の追加制限だった。
現在は `--joint-speed-cap 0`（既定）でURDF上限を使用し、`--joint-speed-cap 0.6` で以前の追加速度制限を再現できる。
launchでは `joint_speed_cap:=0.6` に対応する。追加制限でURDF上限を超えることはできない。
到達不能目標でも角度・速度制限を超えた指令は出さず、制限到達率と残差を残す。

初期姿勢は `[0, -0.6, 0.9, -0.3] rad`。
この付近では位置ヤコビアンはランク3で、位置補償の自由度がある。
これは衝突回避を最適化した姿勢ではない。既存アームURDFの多くの衝突形状は無効化されているため、
実機での使用前に機体・プロペラ・配線との干渉と実用可動域を確認する必要がある。

## 観測入力と実機への移行

初期評価では `/gimbalrotor/ground_truth` (`nav_msgs/Odometry`) を入力にする。
既存シミュレータ設定の約1 mm / 0.001 radの観測ノイズはそのまま。
先端の採点には、入力に使ったFK結果ではなく `/gazebo/link_states` の
`gimbalrotor::arm_joint4_link1` の実測姿勢と、そのリンクからTCPまでの固定変換を使う。
グリッパ内部の回転軸 `arm_joint5_link1` はTCPの固定祖先ではないため、真値の基準には使わない。
FKによる推定との位置不一致RMSも出力し、座標変換の取り違えを見つけられるようにした。

実機では `--control-only` を使用する。このモードは離陸・着陸・機体への試験入力を行わず、
明示的なサービス呼び出しで先端保持を有効にする。

```bash
source /home/leus/ros/jsk_aerial_robot_ws/devel/setup.bash

# mocap。観測座標がfcと一致する場合のみ、外部変換は単位変換でよい。
rosrun gimbalrotor arm_world_eval.py --control-only \
  --pose-topic /gimbalrotor/mocap/pose --pose-type pose --world-frame world

# 十分に整定したホバリング中に実行。現在TCPのワールド目標を固定する。
rosservice call /arm_world_hold/set_enabled 'data: true'
rosservice call /arm_world_hold/set_enabled 'data: false'
```

FAST-LIOでは `--pose-type odom --pose-topic <実際のOdometryトピック>` に切り替える。
トピック名を決め打ちしない。`--world-frame` は実際の `header.frame_id` に合わせる。
FAST-LIOのローカル地図座標でも、その座標系が時間的に固定されていれば定位の基準になる。
地図リセットや再初期化をまたいで同じワールド目標を使ってはいけない。

観測がマーカー・LiDAR・IMUなどのセンサ座標の姿勢なら、校正した
`T_sensor_fc` を `--sensor-to-base x y z roll pitch yaw` で与える。
この変換は **観測姿勢の右から掛けるセンサ→fcの変換**。
観測ワールドと別の作業ワールドを使う場合は、上流でその間の変換も適用する。
空でないframe_idが設定と異なる入力は拒否する。単に名前を変えても座標は校正されない。

位置姿勢と関節角は有効なヘッダ時刻を必須とし、到着後0.3秒・データ時刻0.3秒、
両入力の時刻差0.08秒を上限にする。最新値の組み合わせであり、厳密な補間同期は未実装。
高速動作では補間同期・速度フィードフォワードが次の改善点になる。
非ホバリング状態または入力切れでアーム補償を無効化し、自動再開しない。
実機の飛行制御・着陸判断は既存の操縦系が担当する。

## take9からの揺れ条件

参照は `/home/leus/rosbag/20261015_gimbal/take9_2026-10-28-19-03-07.bag` のみ。
`/gimbalrotor/mocap/pose` と飛行状態・ナビゲーション指令を読み取った。
ホバリング状態はbag開始後73.806〜101.884秒。
離陸・着陸状態境界の前後3秒と、ナビゲーション指令の前1秒〜後4秒を除外し、
残った10秒窓6個のうち位置RMSが中央値の窓を選んだ。
選定区間はbag開始後 **80.010秒〜約90.010秒**。
選択は受信時刻、再生波形の時間軸はmocapヘッダ時刻を使う。
受信時刻には最大159 msのまとめ書き間隔があるが、この窓のヘッダ最大間隔は約29 ms。
ヘッダの代表レートは約121 Hz。

各軸の平均を引き、姿勢は平均姿勢に対する局所回転ベクトルで表す。
長周期の漂いも含み、都合のよいハイパス処理はしない。

| 量 | x / roll | y / pitch | z / yaw |
|---|---:|---:|---:|
| 位置RMS [mm] | 23.9 | 71.0 | 37.8 |
| 位置peak-to-peak [mm] | 74.6 | 256.6 | 164.0 |
| 回転ベクトルRMS [deg] | 2.02 | 1.19 | 5.68 |

合成RMSは位置83.9 mm、姿勢6.14°。
これは選択した1区間における変動であり、機体全般の性能保証やセンサノイズの標準偏差ではない。

標準の動作確認条件は **25%**。100%は到達範囲・速度制限を見るストレス試験とする。
初めと終わりの2秒は入力をなめらかに減衰させる。
元bagの位置残差はGazeboワールド軸に対応させ、局所姿勢残差は基準ヨー角に合成する。

**この波形は機体の位置・姿勢の目標値として投入するため、実機軌道の厳密な再現ではない。**
機体の飛行制御により減衰・遅延し、アームの反力でも変わる。
そのため採点時に実際のベース変動を別に記録する。
ベースの記録は選択した姿勢観測経路の値なので、追加の観測ノイズを入れた試験ではそれも含む。
先端の採点用Gazebo真値には、追加の観測ノイズを入れない。
厳密な再現性が必要な次段階では、動的な風・外力試験と、姿勢を拘束した運動学試験を分離する。
観測値だけにノイズを加える試験は、物理的なベースの揺れの代用にはしない。

## 離陸〜着陸の標準シナリオ

1. 観測・関節角・Gazeboリンク真値と指令接続を待ち、非武装を確認する。
2. IMU変換出力の開始を待ち、さらに3秒の校正待ちを置く。地上でアームを3秒かけて初期姿勢へ移す。
3. 武装状態を確認して離陸し、ホバリング状態を待つ。
4. 高度1.2 mで8秒整定する。
5. 初期姿勢へ戻して整定後、TCPのワールド目標を固定する。
6. **アーム固定**で10秒間の揺れ入力を与えて記録する。
7. ベースとアームを戻して整定する。
8. 同じワールド目標・同じ揺れ入力で **先端定位あり** の10秒を記録する。
9. 揺れ入力を止め、アームを初期姿勢へ戻してから着陸する。
10. 非武装まで確認し、CSV・JSON・比較グラフを保存する。

途中で入力切れ・飛行状態逸脱・高度0.4 m未満・水平逸脱0.7 m超が発生した場合は中断し、
補償と揺れ入力を止めて着陸を要求し、部分結果を残す。
これは正常稼働中のROSに対する処理であり、プロセス強制終了や通信断でも着陸を保証するものではない。

## 実行

```bash
source /home/leus/ros/jsk_aerial_robot_ws/devel/setup.bash

# 元bagから試験波形・統計・グラフを再生成
rosrun gimbalrotor analyze_base_sway.py \
  /home/leus/rosbag/20261015_gimbal/take9_2026-10-28-19-03-07.bag \
  --output "$(rospack find gimbalrotor)/evaluation/base_sway"

# Gazebo起動から離陸・比較・着陸まで。別のGazeboを起動していない状態で使う。
roslaunch gimbalrotor arm_world_eval.launch scale:=0.25 output:=/tmp/arm_world_eval

# 既に本モデルのGazeboを起動済みの場合は評価ノードのみ
rosrun gimbalrotor arm_world_eval.py \
  --sway "$(rospack find gimbalrotor)/evaluation/base_sway/take9_2026-10-28-19-03-07_sway.npz" \
  --scale 0.25 --output /tmp/arm_world_eval

# 純粋な数値テスト（ROS master / Gazeboは不要）
python3 "$(rospack find gimbalrotor)/test/test_arm_world_core.py"
```

GUIを見る場合は `headless:=false`。
`--position-noise 0.001 --angle-noise-deg 0.05 --latency 0.02` で
制御に渡す観測だけへ追加のノイズ・遅延を与えられる。シミュレーション専用で、seed既定値は42。
遅延を入力の鮮度・時刻差上限より大きくした場合は、設計どおり補償が無効になる。

出力の `samples.csv` は先端位置・姿勢誤差、ベース6軸状態、関節角、試験入力、制限到達フラグ、
FKによる推定誤差を記録する。`summary.json` はRMS・95%点・最大値・制限到達率と
フェーズ遷移・着陸完了を記録する。`comparison.png` は位置と姿勢の誤差を別々に比較する。
新しいCSVには速度制限と角度制限のフラグを分けて記録し、指令関節角と実測の差も残す。
summaryにはURDFから読んだ速度・トルク上限も保存する。

記録した比較試行を3D動画にするには、ROS環境をsourceした上で
`python3 script/render_arm_world_video.py <結果ディレクトリ>` を実行する。
MP4はGazebo画面の録画ではなく、観測ベース姿勢・関節角からの模式的な機体/アーム再構成と、
独立したGazebo先端真値の再生。前後の離陸・着陸部分は動画には含まれない。

実際のURDFメッシュと材質を使ったRViz描画動画は `script/render_arm_world_rviz.py` で生成する。
既存のROSや画面に干渉しないよう、未使用の専用ROSポートとXvfb画面を使う。
RVizのPythonバインディング、Xvfb、ffmpegが必要。

```bash
source /home/leus/ros/jsk_aerial_robot_ws/devel/setup.bash
ROS_MASTER_URI=http://127.0.0.1:11329 ROS_HOSTNAME=127.0.0.1 \
ROS_HOME=/tmp/arm_world_rviz_ros QT_QPA_PLATFORM=xcb LIBGL_ALWAYS_SOFTWARE=1 \
xvfb-run -a -s '-screen 0 1600x900x24 +extension GLX +render -noreset' \
python3 script/render_arm_world_rviz.py evaluation/gazebo_take9_quarter_final
```

出力は `arm_world_rviz.mp4`。前半は機体全体、後半はアーム拡大。
ベース姿勢とアーム4軸は記録した試験値を再生し、実際のRobotModelを描画する。
CSVに残していないジンバル角・グリッパ開閉角はゼロ表示なので、全関節を含むGazebo画面の完全録画ではない。
ピンクの十字がワールド固定目標、緑の点がGazeboで採点した実先端位置。

100%条件での追加速度制限とXL430上限の比較動画は、次のように2試行の補償ありログを並べて生成できる。
各試行の固定目標を描画原点に平行移動する。別フライトのため、ベース軌跡は完全には一致しない。

```bash
# 上記と同じ専用ROS_MASTER_URI / Xvfb環境で実行
python3 script/render_arm_world_rviz.py evaluation/gazebo_take9_full_final \
  --compare-result evaluation/gazebo_take9_xl430_12v --fps 15
```

`script/analyze_arm_world_limits.py <結果ディレクトリ>` では、記録済みベース軌跡を固定した
理想サーボの運動学リプレイで速度上限だけを変えて比較する。
瞬間ごとの位置のみの逆運動学（速度・姿勢タスクなし）と、最初の関節からの最大到達半径の
三角不等式による上界も計算する。前者は複数初期値からの数値解で大域最適の保証はない。
後者を超える目標は速度を上げても届かない。Gazeboの動力学試験と運動学解析は別の結果として扱う。

## 次の設計判断

位置だけを固定する作業なら本方式を出発点にできる。
挿入などで姿勢も厳しい作業では、作業に必要な姿勢1軸を明確にし、
残る姿勢2軸を許容するか、ベースの姿勢制御と協調する必要がある。
一般の6自由度をアームだけで固定する要求なら、独立な手首自由度を追加する設計が必要。
次の実機評価では、先端側にもmocapマーカーを置いて独立に測ると、
エンコーダとFKだけでは見えないたわみ・ガタ・TCP校正誤差まで評価できる。
